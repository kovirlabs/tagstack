Retry backoff for the billing webhook

Conversation with Atlas · started Nov 7, 2026, 2:02 PM UTC

You

Our Stripe webhook handler fails about 2% of the time when the ledger database is busy. I want to retry with exponential backoff. What delays should I use, and can you show me Python for it?

Atlas

Thought for 6 seconds

The failures are transient lock contention, so retrying is safe as long as the handler is idempotent. Plain exponential backoff makes every worker retry at the same moments; adding full jitter spreads them out. Stripe itself retries for up to three days, so the in-process retries only need to cover a few seconds before giving up and returning a 500.

Use exponential backoff with full jitter: each retry waits a random time between zero and a cap that doubles every attempt.1 The delay for attempt n is:

tn = random ( 0 , min ( tmax , b ⋅ 2n ) )

Here is a small helper you can wrap around the ledger write:

import random
import time

def with_backoff(fn, attempts=5, base=0.1, cap=3.0):
    """Call fn, retrying with full-jitter exponential backoff."""
    for n in range(attempts):
        try:
            return fn()
        except LedgerBusyError:
            if n == attempts - 1:
                raise
            time.sleep(random.uniform(0, min(cap, base * 2 ** n)))

You

Makes sense. Should the event-id check happen before or after the retry loop?

Atlas

Before it. Record the event id in the same transaction as the ledger write, and skip the event if the id is already there.3 That way a retry after a timeout that actually committed won't charge the ledger twice.
